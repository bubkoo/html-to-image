# Empty video surfaces before media data

The root cause is media readiness, not a failed image request. `currentSrc` identifies a selected resource even when `readyState === HAVE_NOTHING` and intrinsic video dimensions are zero. The former path creates a 0×0 canvas, gets `data:,`, and tries to load that value as an image. An element without a selected resource instead tries to load an empty poster URL. A video with no poster and no media image displays its styled empty box. The scoped fix returns a transparent default-size canvas image for that state, preserving computed background, border and geometry. Normal decoded-frame and poster paths remain unchanged.

The same twelve source tests fail nine / pass three before, then pass all twelve. The three original actual decoded-video aspect-ratio cases remain passing. New modes use no source, a real selected HTTP media request that deliberately supplies no frame bytes, and pending play/pause. No media getters are mocked. Cleanup removes src and calls load() to abort the request. The same fixture is used for ESM/UMD and mobile smoke.

## Poster history is an open boundary

A separate WebKit observation has identical recorded public state, including source markup/currentSrc/readyState/paused/played/currentTime/seeking/networkState, but red native poster pixels initially and blue background after a pending play/pause. A positive-size canvas drawImage of either video yields transparent pixels and does not expose the poster. The archived observation establishes this specific ambiguity, not a theorem about every possible browser API. Consequently a blanket readyState-based poster fallback is not shipped. Caller display history or an accurate non-mutating browser observation would be needed to distinguish these scenes; no whole-video or whole-#585 completion is claimed.
