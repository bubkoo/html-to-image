## A separately reproduced acknowledgement gap

The installed Firefox 157.0 Juggler handler for `Heap.collectGarbage` notifies child GC/CC and forces parent collection; it does not await child completion. Its SHA256 and the [upstream source](https://github.com/microsoft/playwright/blob/main/browser_patches/firefox/juggler/protocol/PageHandler.js) are recorded. GC/CC file logging follows [Firefox's documented flags](https://firefox-source-docs.mozilla.org/performance/memory/gc_and_cc_logs.html), without `MOZ_CC_ALL_TRACES` changing collector optimizations.

Two controlled experiments run ten iterations each: a main-page round trip and an actual persistent test iframe round trip. Each iteration creates and removes an owned document tree, requests one GC, reads incomplete-log filenames immediately at protocol return, evaluates a no-op in the target content frame, then reads filenames again. There is no sleep, polling-to-pass or additional collection between these observations. An independent owned property in the completed GC heap graph identifies the active process; other processes may still be writing and are retained as negative controls.

All 20 returns have an incomplete GC/CC log for the active process; all 20 target-frame round trips have none. Complete before/after records and both processes' raw graphs are in the 96-file acknowledgement archive. This establishes a request/completion synchronization gap in the pinned test toolchain. Log closure alone is not a universal guarantee that every unreachable object collects. Earlier canary experiments used page.evaluate to read results, implicitly adding the same content barrier; they therefore did not show that the request itself waits for the child.
